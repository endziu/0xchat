# 0xChat security review

## Architecture and data flows

0xChat has a Preact browser client built with Vite, a Bun HTTP API, a SQLite database, an app-shell service worker, and optional Web Push delivery through `web-push`. A CLI shares the browser's message protocol. VitePress documentation runs on the same origin as the browser app. Live delivery uses **Server-Sent Events (SSE), not WebSockets**.

1. The browser generates a secp256k1 identity with `crypto.getRandomValues`, derives its Ethereum-style address, and saves the keypair in local storage. Registration publishes the address and its address-bound public key after a signed challenge. Login signs a separate challenge and obtains a bearer session.
2. Before sending, the client verifies that the partner's public key derives to the intended address. It encrypts a separate copy for the recipient and for the sender, signs one envelope containing both copies, and sends it under the sender's session.
3. The API checks the session, signature and envelope, stores the ciphertext copies, and relays the envelope to both participants through SSE. History and recovery endpoints return ciphertext. The receiving client verifies the signature and participant pair before authenticating/decrypting its copy.
4. An authenticated recipient opening starts the sender-selected lifetime. Before opening, retention is 24 hours after server acceptance. Queries exclude expired messages immediately; a sweep deletes expired rows every 30 seconds. Either participant can clear both directions of a conversation. Live clients receive deletion/lifecycle events; disconnected clients reconcile when they return.
5. Push sends a **null payload** to registered browser endpoints. The service worker shows only “0xChat / New message,” then focuses the app or opens `/chat`. Its cache contains the app shell and static assets, not API responses, tokens or messages.

**What the server can see:** both addresses, public keys, the relationship graph, message IDs/signatures, exact plaintext UTF-8 byte lengths inferred from ciphertext lengths, acceptance/opening/expiry times, signed lifetimes, and global message acceptance order. It also sees request IPs, live connections and attention updates, session timestamps, and address-associated push endpoints and subscription keys. SQLite retains today's DAU HMAC key and identity hashes, plus historical aggregate counts. The day's hashes are linkable to known addresses by someone with that key; deleting yesterday's key limits historical linkage in the logical database. Names/labels remain local. Debug logging additionally records request IP/path and message relationships; some warning/error identifiers are logged even without DEBUG.

**Encryption design:** this is a custom ECIES-like message protocol built from established primitives. For each encrypted copy, the sender generates a fresh ephemeral secp256k1 key and performs ECDH with that copy owner's long-term identity public key. HKDF-SHA-256 derives an AES-256-GCM key from the compressed shared point, using the ephemeral public key as salt and `0xChat AES-GCM v2` as context. Each copy receives an independent random 96-bit IV. GCM authenticated data binds protocol version, a random 128-bit message ID, sender, recipient and TTL; an EIP-191 signature additionally binds both ciphertexts, ephemeral public keys and IVs. Server acceptance/opening/expiry times and message ordering are outside that signature. There is no ratchet or forward secrecy. Evidence: `src/shared/crypto.ts:15`, `src/shared/signed-message-envelope.ts:21`, `src/shared/message-envelope.ts:78`.

## Which guarantees hold

| Intended guarantee | Code assessment |
| --- | --- |
| 1:1 E2EE; the server stores/relays only ciphertext | **Holds for message content with an honest client and uncompromised endpoint keys.** No server-side message decryption or plaintext storage was found. The server also stores substantial unencrypted metadata. An active operator serving a modified client can steal keys/plaintext; later identity-key compromise decrypts recorded history. |
| Browser-generated secp256k1 identity; show/export/import | **Implemented.** Generation uses browser CSPRNG and noble; viem signs messages. Import validates format and derives the address. Browser export is raw reveal/copy, without encryption or reauthentication; persistence is plaintext. |
| Contacts by address, QR or conversation link | **Implemented.** Parsed addresses drive local `/chat/:address` navigation. A scanned URL supplies an address only; its origin/scheme is not followed. Labels are local. |
| Accept only correctly signed/authenticated messages addressed to the client | **Holds for displayed incoming plaintext.** The client checks signer, participant pair and GCM authentication. Its own signed sender-history copies are intentionally accepted too. This does not authenticate server lifecycle/control events, prove freshness, or make rejected-message incidents visible to the user. |
| Configurable expiry and “clear for both” | **Enforced logically by the honest server and client lifecycle.** TTL is 5 seconds–24 hours **after recipient opening**, not after sending. A message opened just before its 24-hour unopened deadline with TTL 24 hours can survive nearly 48 hours after acceptance. Clear deletes matching server rows and updates connected clients. It cannot erase a participant's saved copy, an offline client's existing copy immediately, or prove deletion by a malicious server; disk/backups need checking. |
| PWA, service worker, Web Push; strip fragments before load | **Implemented.** The fragment guard runs before the app module, and its exact hash is CSP-authorized. Production registers the worker; API/SSE are excluded from its cache. Push contains no message text, address or conversation identifier. |

### Trust assumptions

| Assumption | Holds up? |
| --- | --- |
| 1. Server/operator or DB leak learns little | **Content: yes for passive observation; metadata: limited.** Ciphertexts alone do not expose plaintext or identity private keys. Stored bearer tokens are hashed. The database exposes relationships and activity; the operator additionally sees traffic and may retain it. Because this operator also serves executable client code, confidentiality from an actively malicious operator is not established by the web deployment. |
| 2. Server cannot alter, resend, reorder or misattribute unnoticed | **Partially.** Signed ciphertexts and participants resist alteration/misattribution. Unsigned timestamps, opening/clear events and server clock permit chronology/lifecycle manipulation. Replay protection is temporary. Invalid deliveries can be silently discarded while recovery advances. Complete omission prevention is impossible against a relay that withholds delivery; authenticated sequences/acknowledgements can expose some gaps. |
| 3. Other users' content is untrusted | **Mostly handled well.** Text/labels/errors render as escaped Preact children; message links are HTTP(S)-only and QR payloads become validated addresses. The generated avatar SVG sink was inspected. A bounded but quadratic link parser remains an availability concern. A valid signature establishes authorship, not harmless content. |
| 4. Browser private key survives injection/dependency compromise | **Does not hold.** Same-origin executable code can read persisted keys/tokens or use the unlocked identity. CSP reduces injection paths but does not isolate permitted bundled code. Encrypted storage would protect locked data, not a compromised active client. |
| 5. Brief possession of an unlocked device reveals little | **Does not hold.** The app loads the identity without a lock, shows available conversations, and reveals/copies the raw key without reauthentication. Burn/import also leaves local relationship metadata behind. |

### Important boundaries behind the findings

- **SEC-01:** storage encryption and a lock help against stored-profile exposure and brief device access. They cannot make arbitrary code executing in an already-unlocked client trustworthy. Nonextractable keys alone would not prevent malicious code from requesting signing/decryption. The app and docs currently share an origin (`site/.vitepress/config.ts:3`); path separation is not a browser security boundary.
- **SEC-03/04:** the server cannot substitute another public key for a known address or modify a signed envelope unnoticed. The attack is to manipulate fields outside the envelope or reuse an authentic envelope. Signing messages with the server's own key would not address a malicious-server threat.
- **SEC-06:** ordinary failed network requests and failed continuation pages preserve the previous committed recovery checkpoint (`src/client/lib/conversation-session.ts:445`, `:467`). Partial additions deduplicate on retry. The initial history baseline is intentionally retained before state reconciliation (`:463`). The defect is specifically successful recovery containing rejected envelopes, not the general checkpoint design. The server cursor HMAC protects scope/bounds from other clients, but its key belongs to the relay and cannot establish completeness against that relay (`src/server/recovery-cursor.ts:14`).
- **Expiry/clear:** an honest recipient can save plaintext, and an operator can save ciphertext; neither can be forced to forget it remotely. Existing client attention checks govern opening/notifications, not device access control. Already revealed plaintext can remain shown while the window is ineligible (`src/client/lib/conversation-messages.ts:218`).

## Web platform and push assessment

- **CSP and headers:** `src/server/constants.ts:25` supplies self-only script/connect/font sources, one exact fragment-guard script hash, `object-src 'none'`, `frame-ancestors 'none'`, `form-action 'self'`, `base-uri 'self'`, `nosniff`, `no-referrer`, and restricted Permissions Policy. There is no script `unsafe-inline` or `unsafe-eval`. Inline styles are allowed. These headers cover JSON/static/SSE responses; Vite development does not establish production policy.
- **SRI:** no production third-party CDN scripts/fonts were found. First-party bundled assets have no SRI attributes. Adding integrity strings to operator-controlled HTML would not independently prevent that same operator from replacing both HTML and assets.
- **CORS/origins:** no permissive CORS response headers or cookie-based ambient session authentication were found. Registration/session challenges bind the claimed origin and clients reconstruct the expected challenge before signing. Origin parsing is not an application-origin allowlist, and SSE admission lacks an Origin check; possession of its unguessable, single-use token is the authorization boundary. An external page cannot obtain a bearer from ambient cookies. No standalone CSRF/cross-origin message-reading exploit was established from these omissions.
- **Service worker/update:** `public/sw.js:29` excludes other origins, non-GET, API/SSE and docs. Navigations are network-first; static assets are cached; activation removes older caches and takes control. The server revalidates HTML/SW, and the explicit update action calls `registration.update()` before reload (`src/server/routes/static.ts:11`, `src/client/hooks/useClientUpdate.ts:16`). Cached ciphertext/plaintext/identity was not found in this worker. The cache/update mechanism inherits the origin's code trust; it is not an independent code-authenticity channel.
- **Push:** `src/server/push.ts:21` sends no payload; `public/sw.js:73` ignores push data. The provider learns its destination endpoint, arrival time, TTL and VAPID sender information, and can correlate traffic with its own device/subscription records. It receives no chat text or sender/recipient address in the payload. The app server knows the address-to-endpoint association. Generic alerts minimize lock-screen content but can still reveal app usage/activity.
- **Deployment facts needing checking:** Bun listens over HTTP and this repository contains no production proxy/TLS configuration or app-added HSTS (`server.ts:21`, `src/server/constants.ts:25`). Production HTTPS redirects, HSTS, database/log/backup permissions and reverse-proxy logs must be verified from deployment configuration. In particular, access logs should avoid SSE query capabilities. The app's own request logger logs pathname rather than the query string (`src/server/router.ts:68`). This is not a claim that the deployed site lacks HTTPS/HSTS or leaks tokens; no live headers were inspected.

## What is already done well

- **Address-bound encryption keys:** registration and client lookup independently derive the claimed address from the public key, preventing relay key substitution (`src/shared/address-bound-pubkey.ts:21`, `src/shared/protocol-client.ts:89`, `:197`).
- **Authenticated message content:** exact envelope schemas, canonical addresses, validated curve points, bounded ciphertexts, signer recovery, participant checks and GCM verification all precede display (`src/shared/message-envelope.ts:106`, `:127`, `:143`; `src/shared/protocol-client.ts:98`). Fresh random keys/IVs and protocol-specific HKDF/AAD are present. No confirmed nonce-reuse, primitive, public-key-validation or signature-bypass defect was found.
- **Server authorization:** message sender must equal the bearer identity and verify cryptographically. Conversation queries are scoped to the authenticated participant; opening is recipient-only; clear covers only that participant pair. SQL values are parameterized (`src/server/routes/messages.ts:70`; `src/server/db.ts:311`, `:385`, `:479`, `:505`).
- **Authentication tokens:** origin/identity-bound random challenges are single-use with expiry; the challenge store has a hard entry cap. Session tokens have 256-bit randomness and only SHA-256 digests are stored in SQLite (`src/server/challenge.ts:16`, `:32`, `:60`; `src/server/routes/auth.ts:96`; `src/server/db.ts:6`).
- **Lifecycle enforcement:** first opening is atomic and never restarts an existing timer. Expired rows are excluded from read/recovery/list/state/open even before cleanup. Request-body limits, ID-batch limits, mutation/recovery rate budgets and SSE admission caps are implemented. Trusted-proxy IP handling does not blindly accept forwarded IPs (`src/server/db.ts:471`; `src/server/http.ts:26`; `src/server/routes/messages.ts:219`; `src/server/trusted-proxy.ts`).
- **Untrusted rendering:** messages, labels and errors use escaped Preact text. HTTP(S) message links display their URL and set `noopener noreferrer`; QR parsing never navigates the supplied origin (`src/client/components/MessageText.tsx:15`; `src/client/lib/message-links.ts:44`; `src/client/lib/address-links.ts:11`). The sole raw HTML sink inserts generated `glyphid` SVG (`src/client/components/AddressAvatar.tsx:11`): the inspected 0.1.0 implementation escapes attributes, hashes the address, emits fixed mosaic elements, and receives canonical addresses/fixed numeric sizes. No confirmed HTML injection path was found.
- **Key transitions/logging:** imports preview a derived address, revoke the old session, guard stale work and clear auth; message stores are identity/partner/token scoped. No intentional browser private-key/plaintext logging was found. CLI identities use exclusive 0600 files, reject symlinks on load, and terminal output strips control characters (`src/client/lib/identity-transition.ts:17`; `src/client/hooks/useMessages.ts:69`; `src/cli/identity.ts:13`, `:34`; `src/cli/main.ts:47`). These controls do not replace browser secret encryption/locking.
- **Push containment:** authenticated bounded mutations, provider HTTPS hostname allowlisting, owner-scoped unsubscribe, five subscriptions per identity and a send timeout reduce abuse; arbitrary-host push SSRF was not found (`src/server/validation.ts:22`, `:45`; `src/server/routes/push.ts:15`, `:55`; `src/server/db.ts:428`; `src/server/push.ts:12`).

## Prioritized fix list — quick wins first

1. **Make existing guarantees explicit now:** document the active-origin trust boundary, no forward secrecy, opening-based expiry, metadata exposure and logical clear semantics. Default the production environment example to no DEBUG and establish log/backup retention. This narrows misleading expectations while larger changes are designed. **SEC-01/02/03/08/11.**
2. **Fix backup feedback and local privacy cleanup:** await clipboard writes; provide failure UI; scope contacts/labels/seen/removal state to the identity and purge on burn. Make URL trimming linear and avoid repeated parsing. **SEC-07/13/14.**
3. **Close server authorization/resource gaps:** tie SSE to session revocation/expiry/account deletion; add history/list read budgets and bounded list pages; verify and cap slow-reader queues. **SEC-05/09/10.**
4. **Update affected tooling using the frozen tree:** resolve the concurrently/shell-quote and source-map-js advisories, then migrate the nested VitePress/Vite/esbuild chain. Re-run full and runtime-only audits and review compatibility. **SEC-12.**
5. **Expose protocol rejection and stop replay resurrection:** make invalid-envelope incidents visible, define recovery quarantine/checkpoint behavior, and persist clear/replay state. Server tombstones must outlive ciphertext and work with authenticated age/epoch limits. **SEC-04/06.**
6. **Add encrypted browser key storage and an actual lock:** explicit unlock, short idle/background policy, protected export, and minimal plaintext lifetime; isolate documentation authority where practical. This protects locked state/device exposure, not arbitrary active same-origin code. **SEC-01.**
7. **Design the protocol changes together:** adopt reviewed ratcheting encryption and authenticated conversation order, opening/clear controls and replay epochs. Include multi-device use, sender-history copies, re-import and offline recovery in the design. **SEC-02/03/04.**
8. **Verify operational retention and transport controls from configuration:** SQLite/WAL/backups, proxy HTTPS/HSTS and query-log treatment. If relationship/traffic privacy is a product requirement, specify a separate metadata threat model before promising it. **SEC-08/11 and deployment checks.**
