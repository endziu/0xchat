Problem
Source separation exists, but one dependency manifest and a full test command that deletes the database and builds the client couple otherwise focused work.
Solution
Enforce import direction, isolate client/server test and dependency ownership, and consider workspace packages only where they support those rules; keep shared protocol ownership explicit.
Evidence
Both sides already use src/shared and have separate TypeScript configurations; cross-tier test imports exist. The root test command clears database/build output before building and testing everything. The server also serves dist; browser HTTP and SSE use relative URLs.
Depth
This strengthens the existing seam; it adds little depth by itself. A directory or package move leaves the history, identity and push interfaces just as demanding.
Deletion test
Removing shared build/test orchestration can concentrate each module’s setup; deleting the directory distinction only moves code. Removing shared protocol modules would duplicate meaningful implementation across callers.
Tests
Provide focused checks without frontend build or database deletion when unnecessary; retain explicit cross-tier integration tests for envelopes, challenges and delivery. Enforce import direction and browser runtime restrictions in tooling: TypeScript include lists alone are not import fences.
Adapter / seam
The HTTP adapter already crosses a real network seam. Exercise the same protocol with controlled test responses and real-server integration tests; a package move does not require a new adapter.
  • Locality: dependency and test ownership
  • Leverage: focused contributor checks
  • Depth: limited without behavior consolidation

Three interpretations, different payoffs

ScopeAssessmentWhat would justify it?
Enforced separation, same repositoryWorth exploring. Start with focused checks and import rules; workspace packages are an option.Repeated setup friction, accidental runtime imports or distinct dependency ownership.
Separate repositoriesSpeculative. Adds protocol versioning and coordination across changes; does not hide behavior.Independent ownership, access controls or release schedules that the current repository cannot support.
Independent deploymentsSpeculative. Separate hosting is possible behind one public origin; different public origins expand the change substantially.A concrete hosting, release or scaling requirement. Different origins require transport configuration, CORS handling, CSP changes and verification that registration/session origin binding remains correct.

Preserve browser-held keys and browser encryption, server ciphertext relay, shared verification, and origin-bound challenges. The proposal is structural; those responsibilities already have meaningful separation.

Top recommendation

Conversation history coordination

Start with conversation history: its split cursor/commit contract has repeated repair history and offers direct depth. Add focused client/server checks as a smaller tooling improvement; defer repository or deployment separation until an ownership or release requirement makes its leverage concrete.
